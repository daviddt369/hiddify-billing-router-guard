# golden: развернуть панель на новом сервере одной командой

> **Чистая установка для нового человека или нового сервера** (без чьих-либо данных): `sudo bash install.sh` в корне репозитория; он сам спрашивает название, домен и контакт (`golden/make_params.py`) и вызывает `golden/install.sh --fresh`. Ниже - то же самое, но с **переносом существующего узла** (его данные из снимка, параметры из закрытого набора). Ноды выхода - `node/README.ru.md`. Чужие части и лицензии - `NOTICE.md`.

После чистой установки панель работает, но выходов ещё нет: роутер строится при подключении первого выхода (`node/ru-attach-wg.sh` или страница «Внешние ноды» панели), до этого пользователи выходить в сеть не смогут (закрыто по умолчанию, а не открыто).

Что это: «золотой стандарт» рабочего RU-узла (панель, маршрутизация, мониторинг, auto-director, анти-шаринг, дашборд) в виде кода и одного установщика. Проверено полной сборкой с нуля в чистой Ubuntu 24.04 и сверкой с рабочим узлом по списку из 162 файлов.

## Что нужно на новом сервере

1. Чистая Ubuntu 24.04 (или 22.04), root, доступ в интернет, в `/root/.ssh/authorized_keys` ваш ключ (настройки SSH узла «только по ключам», без ключа они не ставятся, чтобы вас не заблокировать).
2. Этот репозиторий (`git clone`, ветка `master` с тегом `golden`).
3. **Закрытый набор** (в репозитории его нет и быть не должно; хранится у вас, лучше в зашифрованной офсайт-копии рядом с обычными бэкапами):
   - `params.env` - реальные значения заглушек `@@NAME@@` (IP, домены, секретный путь CDN, контакт поддержки, название продукта). Образец: `golden/params.example.env`.
   - `vendor/admin-v2.tar.gz` - сборка нового дашборда Admin V2 (чужой собранный код, 4 МБ).
   - снимок данных - каталог `disaster-recovery/snapshot.sh` (БД, пользователи, ключи, сертификаты, секреты).

## Команда

```bash
git clone https://github.com/daviddt369/hiddify-billing-router-guard.git && cd hiddify-billing-router-guard
sudo bash golden/install.sh --params /root/params.env --vendor /root/vendor --data /root/snapshot/<дата>
```

Без `--data` ставится только платформа и наш слой (на чистой базе, без пользователей). Отдельные этапы: `--stages "overlay vendor post"`.

Этапы: `base` (Hiddify v12.0.0 и аддоны) → `overlay` (наши файлы, список `MANIFEST.tsv`, заглушки подставляются из `params.env`, заменённые файлы копируются в `/root/golden-backup-<время>`) → `vendor` (Admin V2) → `pins` (xray v26.7.28, скачивается с официального релиза и сверяется по sha256) → `post` (компиляция, таблицы слоя маршрутизации, перезапуск панели) → `data` (восстановление данных, `disaster-recovery/restore.sh`) → `router` (сборка конфига локального роутера `/etc/xray-router` из восстановленной базы) → `enable` (включение наших служб и таймеров из `UNITS.enabled`) → `verify` (все файлы манифеста = эталон, плюс дымовой тест панели `smoke.py`).

Откат слоя: `sudo bash golden/rollback.sh /root/golden-backup-<время>`.

## Что остаётся руками (скриптом не сделать)

- DNS всех доменов на новый IP; в кабинетах Gcore / Selectel сменить origin на новый IP; проверка через CDN (до этого DNS/CDN на сервер не переключать).
- Telegram-вебхук (перерегистрируется сам на домен; проверить).
- Сертификаты: выпускаются при применении настроек, когда домен уже указывает на сервер.
- Внешние ноды DE / NL: этот эталон только для RU-узла. Новый выход и подключение выходов: `node/README.ru.md`. WireGuard-пир на выходе не привязан к IP RU (в его конфиге нет `Endpoint`), так что смена IP RU его не ломает; проверьте только фильтры по IP у хостера.

## Как обновлять эталон и ловить дрейф

На машине с ключом к узлу (только чтение на узле):

```bash
python golden/capture.py --ssh "ssh -i ~/.ssh/ключ -o BatchMode=yes root@IP" --params ~/VPN-GOLDEN-PRIVATE/params.private.env
git diff --stat golden/        # что изменилось на узле с прошлого снятия = дрейф
```

`capture.py` забирает файлы из `FILES.list`, заменяет личные значения на заглушки, пишет `overlay/` и `MANIFEST.tsv` и сам проверяет, что в результате нет ни ваших значений, ни IP, ни секретоподобных строк. Новый файл узла добавляется строкой в `FILES.list`.

## Репетиция «с чистого листа» на своём компьютере (как проверялось)

1. Официальный образ Ubuntu 24.04 для WSL (`cloud-images.ubuntu.com/wsl`), проверка sha256, `wsl --import`, в `/etc/wsl.conf` `systemd=true`.
2. Этапы без данных (с интернетом): `install.sh --stages "base overlay vendor pins post"`.
3. **Перед данными отключить сеть**: `ip route del default` (и `ip -6 route del default`) и держать дистрибутив запущенным (`wsl -d ... sleep infinity`), проверить `curl` на api.telegram.org и свои ноды. Правила iptables для этого НЕ годятся: Hiddify при запуске вставляет `-I OUTPUT ... ACCEPT` выше любых ваших правил, а перезапуск WSL стирает их. С данными узел умеет писать пользователям в Telegram, запрашивать сертификаты и подключаться к нодам по настоящим ключам WireGuard.
4. Этапы с данными: `install.sh --stages "overlay vendor post data router enable verify" --data ...`.

Результат последней репетиции с нуля (вторая чистая Ubuntu 24.04, без ручных шагов): 162 из 162 файлов совпали с узлом, дымовой тест панели без ошибок, в конфиге роутера 15070 правил (как на узле), xray 26.7.28, наружу ничего не уходило.

## Версии, которые не закреплены

HAProxy берётся из PPA, на RU сейчас 3.3.8, на новом сервере будет свежая 3.3.x. `hiddify-core` и остальные бинарники ставит базовый установщик Hiddify v12.0.0.

## Что в эталон не входит

- Переводы панели (`.po` / `.mo`): отличаются от базовых только двумя новыми строками статуса подписки; при установке они остаются на английском, пока их не добавить отдельным шагом.
- `redis.conf` (содержит сгенерированный пароль, на новом сервере создаётся заново) и агент мониторинга хостера (zabbix).
- Узлы DE / NL (отдельный эталон).
