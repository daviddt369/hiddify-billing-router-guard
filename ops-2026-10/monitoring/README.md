# CP-08 · сквозной мониторинг RU, DE (.190), NL (.238) — «vpn-watch» (закрывает F-07)

**Статус: написан и проверен на стенде (16 тестов на настоящих router/выходах стенда, мутационная проверка, установка/таймеры/удаление через настоящий systemd). На production НЕ устанавливался.**

Одно небольшое приложение (Python 3, только стандартная библиотека, ≈700 строк, `src/vpn_watch.py`) на каждом из трёх узлов. Hiddify, Xray, HAProxy, файрвол не трогает: читает, пробует и пишет только в `/var/lib/vpn-watch`.

## 1. Что оно видит (и какую находку этапов 1–2 это закрывает)

| Что проверяется | Где | Как | Находка |
|---|---|---|---|
| **Что получает пользователь**: через входы router (20811 = DE, 20813 = NL, 20808 = AUTO) запрос во внешний мир → **выходной адрес** сравнивается с ожидаемым | RU, каждую минуту | `curl --socks5-hostname` | F-02, F-07: «страна ушла в чужую/молчит» |
| **Каждый VLESS/Trojan-узел отдельно** | RU, раз в 5 мин | временный клиент Xray из **живого** конфига router, по одному входу на узел; WG-узлы — `curl --interface wgN` | F-01, F-07: «8 из 13 мертвы, сигнала нет»; резерв внутри страны («живых узлов k из n») |
| **WireGuard на RU** (TUN-интерфейсы Xray, `wg(8)` их не видит): «отправлено растёт, принято нет» = мёртвый обратный путь | RU | счётчики `rx_packets/tx_packets` | сигнатура дефекта CP-07 |
| **WireGuard на выходах**: свежее рукопожатие | .190, .238 | `wg show` | F-01 |
| **Дрейф конфигурации router**: у `balancer-s*` обязан быть `fallbackTag=block`; outbound `block` на месте; «конфиг изменился» (информационно) | RU | чтение `/etc/xray-router/config.json` | F-02 (CP-05) |
| **Новый публичный порт** (эталон запоминается при установке) | все три | `ss -tulnp` | F-04 (админка :3000), F-06 |
| **«Выход изменился без вас»**: отпечатки путей HAProxy, структуры inbound'ов Xray (ML-KEM), версии Hiddify, `wg-rude.conf`, адреса/allowed_clients AdGuard | .190, .238, RU | хэш от ключей/структуры (содержимое не хранится) | F-01 (ловушка ML-KEM), F-06, F-04 |

| **Сертификаты**: IP-сертификаты короткоживущие (≈6 суток, обновляются каждые 2–3 дня) — свои пороги 2 дня/1 день; остальные 14/5 дней | все три | `openssl x509` | F-07 |
| Службы (`systemctl is-active`), таймеры, диск, память, нагрузка | все три | | F-07 |

| Ошибки DNS в журнале router (110 за сутки были «closed pipe») | RU | `journalctl` | F-03 |
| Собственный выход в интернет (адрес = ожидаемому) | .190, .238 | `curl` | F-07 |
| Доступность 443 выходов с RU (TCP) | RU | connect | F-07 |

## 2. Оповещения

* Telegram, **отдельный бот и чат** для мониторинга (бот только отправляет). Токен/чат владелец кладёт в `/etc/vpn-watch/telegram.env` (600) на каждом из трёх узлов; в код, репозиторий и журнал они не попадают.
* Гистерезис: критическое — после **3** подряд неудачных запусков (≈3 мин; для узлов — 3 запуска по 5 мин = 15 мин), предупреждение — после **5**; повтор раз в **3 ч**, пока сломано; сообщение «✅ восстановлено»; одно сообщение на запуск (без шквала); недоставленные сообщения копятся в очереди (до 20) и уходят позже; ежедневная сводка в 09:00 (раз в сутки — это и «пульс»: если сводки нет, перестал работать сам мониторинг или Telegram).
* События (смена эталона, перезапуск router, «выход изменился») приходят один раз, как ℹ️/🟠.

## 3. Где это ставится и какая нагрузка

`install.sh ru|de|nl`: `/opt/vpn-watch/vpn_watch.py`, `/etc/vpn-watch/{config.json,telegram.env}` (600), `/var/lib/vpn-watch/` (700), юниты `vpn-watch.{service,timer}` (раз в минуту), на RU ещё `vpn-watch-nodes.{service,timer}` (раз в 5 мин). Юниты: `Nice=10`, `IOSchedulingClass=idle`, `ProtectSystem=full`, `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`, запуски сериализуются блокировкой (быстрый и узловой делят одно состояние).
Нагрузка: быстрый запуск — доли секунды CPU (3 запроса через router, пара `systemctl`, `ss`); проверка узлов раз в 5 минут поднимает на 5–15 секунд временный Xray (≈30 МБ) и делает ≈13 запросов на ≈1 КБ. Временный конфиг с учётными данными узлов живёт в приватном `/tmp` юнита (0600) на время проверки и удаляется.
Влияние на пользователей: нет (проба идёт в отдельный временный клиент и во входы router, не через первый хоп — антишаринг её не видит).

## 4. Порядок установки (выполняет владелец; я готов выполнить по согласованию)

1. **Сначала исправления безопасности, потом мониторинг** — иначе эталон публичных портов «запомнит» лишнее (например, :3000 на .190). `install.sh` в конце печатает список запомненных портов — просмотрите его глазами; если лишнее — исправьте и `python3 /opt/vpn-watch/vpn_watch.py baseline`.
2. Создать отдельного Telegram-бота мониторинга (@BotFather), чат; заполнить `telegram.env`; `python3 /opt/vpn-watch/vpn_watch.py test-telegram`.
3. Порядок узлов: .238 → .190 → RU (RU последним: там самые важные проверки).
4. Включить в `config.nl.json` проверку `auto_update` (`"enabled": true`) после применения CP-03.
5. На RU при необходимости заполнить `expected_dead_nodes` (например `["6"]`, пока не применён CP-07), чтобы заведомо мёртвые узлы не оповещали.

## 5. Проверка до / после, откат

* До: `command -v python3 curl openssl xray` (RU: нужен `xray`); свободное место; `systemctl is-active` ключевых служб.
* После: `deploy/verify.sh` (таймеры, последние запуски, список результатов, права файлов, очередь сообщений); `python3 /opt/vpn-watch/vpn_watch.py status`; через сутки — ежедневная сводка в Telegram.
* Откат: `deploy/uninstall.sh` (удаляет программу и таймеры; конфиг и состояние оставляет), `deploy/uninstall.sh --purge` (удаляет всё). Автоматического отката не требуется: приложение не меняет ничего вне своих каталогов.

## 6. Результаты на стенде (`test/`)

* `test_vpn_watch.py` — 16 тестов на настоящих router и выходах стенда с поддельным Telegram-сервером: здоровая система молчит; смерть страны → ровно один 🔴 после третьего запуска, без повторов, затем «восстановлено»; неверный выход → «трафик пошёл не туда»; router остановлен → алерты по службе и входам; узлы проверяются по отдельности, мёртвый выход называет свои узлы и «резерва нет»; ожидаемо мёртвые не оцениваются; новый публичный порт; пороги сертификатов по шаблонам; дрейф `fallbackTag`; отпечаток меняется один раз; очередь при недоступном Telegram; ежедневная сводка раз в сутки; WG: TUN «TX растёт, RX нет» → 🔴, простаивающий туннель → только медленное 🟠, ядерный WG с протухшим рукопожатием; WG-узел находится по адресу туннеля.
* `test/FINAL-test-run.txt` — итоговый прогон всех 16 тестов и 5 мутационных проверок: тесты **падают**, если сломать гистерезис, правило «WG шлёт, но не принимает», обнаружение нового порта, проверку `fallbackTag` или пороги сертификатов (контроль без поломки — зелёный).
* `install-uninstall-on-stand-with-systemd.txt` — установка, эталон портов, таймеры реально срабатывают, `verify.sh`, `uninstall`, `--purge` не оставляют следов.
* Лабораторный факт, на который опирается проверка WG-узла: `curl --interface wg0` через настоящий Xray с ядерным TUN даёт «нет ответа» при мёртвом обратном пути и корректный выход после исправления (`../CP-07-wg190-snat/test/dataplane-masquerade-vs-snat.txt`).

## 6a. Что не проверено / ограничения

* Проверки на **реальных** RU/.190/.238 не запускались (на проде не тестируем): имена служб, пути сертификатов и номера слотов взяты из чтения этих серверов (`deploy/config.*.json`); первый запуск покажет расхождения как предупреждения, а `status` — полный список.
* Нет внешней точки наблюдения (это не «пинг из интернета»). Дёшево закрыть сторонним сервисом проверки доступности (по решению владельца); ежедневная сводка в Telegram служит «пульсом».
* Telegram с RU идёт напрямую; если с RU он недоступен, а с выходов доступен, оповещения о RU придут с задержкой после восстановления связи (очередь) — для критичных случаев рядом работают оповещения выходов (они видят, что RU не стучится: растёт «молчащий» туннель).
* Сертификаты IP: если их обновление остановится, предупреждение придёт за 2 дня до окончания (6-суточный срок).
