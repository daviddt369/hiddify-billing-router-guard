# Бриф для аудитора (Codex): резервный вход VK TURN на RU

Автор: Claude. Дата: 2026-10-23. Статус: НЕ установлено ни на RU, ни на DE/NL. Репетиция выполнена только на стенде (WSL `hiddify-stand`). Полное описание — `README.md` рядом.

## 1. Что проверяем
Второй, независимый вход для клиентов на случай отказа Gcore: Android-клиент qWDTT → relay-серверы VK (TURN) → UDP-порт на RU → qWDTT-сервер (GPL-3.0) в изолированном network namespace → мост в SOCKS-inbound xray-router (20808, AUTO) → DE/NL. Основной вход (Gcore) и подписки не меняются.

## 2. Что просим подтвердить или опровергнуть
1. **Изоляция.** Установка не меняет существующие файлы, правила iptables/nft, маршруты, ip rule, sysctl, службы и слушающие порты (кроме нового UDP-сокета). Проверка: `install.sh` сам снимает слепок до/после и печатает «UNCHANGED»; воспроизвести — `multiloc-stand/work/stage2/vkturn/rehearse.sh`.
2. **Единственное изменение firewall** — `iptables -I INPUT -p udp --dport 47213 -j ACCEPT` (`firewall-open.sh`, запускает владелец). Проверить, что ни один другой порт (в т. ч. TCP 56000 служебного HTTP API сервера qWDTT, 56001/56002) наружу не доступен: сервер слушает только внутри netns на 10.99.0.2 и 0.0.0.0:56001 внутри netns; на хосте единственный публичный сокет — socat UDP 47213.
3. **Исходный код qWDTT-сервера** (`server/`, коммит в `bin/SOURCE_COMMIT.txt`, ~4.8k строк Go): нет телеметрии и скрытых соединений (наружу: только Telegram Bot API и api.ipify.org, и то лишь при заданном токене бота — мы токен не задаём); `exec.Command` вызывает только iptables/nft/ip/sysctl (внутри netns — действует только там); админ-API выключен (нет `-admin-listen`). Просим независимо перечитать `server/{main,connections,wireguard,nat,raw,keys,obfs,profile_api}.go` и зависимости `go.mod` (pion/dtls v3.1.5, wireguard-go 20250521, x/crypto 0.51).
4. **Цепочка поставки.** Бинарник собран нами из этого коммита: Go 1.27.3 (контрольная сумма с go.dev сверена скриптом `build-server.sh`), модули по `go.sum`, `CGO_ENABLED=0 -trimpath`. Штатный `deploy.sh` приложения НЕ запускался. `install.sh` сверяет sha256 бинарника (`EXPECT_SHA`). Просим воспроизвести сборку и сверить sha256 (`bin/wdtt-server.sha256`).
5. **Попадание трафика в router.** Мост: netns → socat 127.0.0.1:1080 → unix-сокет `/run/vkturn/s.sock` (0600, root, каталог 0700) → socat на хосте → `127.0.0.1:20808`. Проверить, что этот путь не даёт доступа в netns к чему-либо ещё на хосте, а UDP не утекает мимо (в xray-ns.json: UDP/53 → dns-outbound, прочий UDP → blackhole, остальное → SOCKS router). Fail-closed router (balancer `auto-director`, `fallbackTag: block`) сохраняется, потому что трафик входит через тот же inbound.
6. **Ресурсы.** Службы ограничены cgroup (MemoryMax 64–400 МБ, CPUQuota 100% у xray и сервера). Проверить, что на RU (2 vCPU, ~1.7 ГБ свободно) хватает запаса и что при отказе резерва основной вход не страдает.
7. **Откат.** `uninstall.sh` + `firewall-close.sh`: после них не остаётся служб, файлов, netns, veth, правил. Проверено на стенде; просим повторить.
8. **Лицензии.** Используем только qWDTT (GPL-3.0; для внутреннего использования без передачи программы третьим лицам обязанностей по раскрытию нет) и PWDTT (GPL-3.0) как возможный клиент ПК. CSQTT и FOCSQ (PolyForm Noncommercial) не используем, исходники в проект не переносились.

## 3. Границы доверия и поверхность атаки
- Снаружи доступно ровно одно: UDP 47213 на RU. Пакеты принимает socat и пересылает в netns на сервер qWDTT. Без знания пароля (HKDF от пароля, обёртка RTP-AEAD, затем DTLS) сервер пакеты молча отбрасывает.
- Пароль владельца: `/etc/vkturn/wdtt/owner.pw` (0600). Один общий пароль на всех тестеров; ротация — перезапись файла и перезапуск `vkturn-server`.
- relay-серверы VK видят зашифрованные пакеты и адрес RU-сервера; содержимого не видят.
- Сервис не доверяет клиенту: клиентские пакеты попадают в netns, где нет ничего, кроме xray TUN и моста к router. Клиент может ходить только туда, куда пускает router.

## 4. Что не проверено (честно)
- Реальный VK TURN (нужны ссылка-звонок VK и телефон владельца): handshake, скорость, переподключение, смена сети, белые списки.
- DNS и TCP наружу из netns на самом RU (на стенде нет интернета через лабораторные выходы). Проверит `check.sh` после установки.
- Совместимость клиента PWDTT с этим сервером (заявлена в README PWDTT).
- Производительность моста socat+xray TUN под нагрузкой.

## 6. Известные слабые места, которые стоит оценить отдельно
- Хостовый socat-мост доступен любому процессу root на RU (unix-сокет 0600): это не расширяет привилегии, но стоит подтвердить.
- socat UDP-relay: для сервера все клиенты выглядят как 10.99.0.1:разные порты; это нормально для сервера qWDTT (сессия по адресу), но означает, что реальный IP клиента в логах сервера не виден.
- Сервер qWDTT запускается с `CAP_NET_ADMIN` внутри netns от root; юнит не использует `ProtectSystem`/seccomp (iptables и TUN внутри netns требуют прав). Просим предложить усиление, не ломающее работу.
- Правило INPUT попадает в `/etc/iptables/rules.v4` при следующем применении Hiddify (он сохраняет живые правила): закрытие обязательно после теста.
